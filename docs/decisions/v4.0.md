# v4.0 decisions

The decisions behind v4.0.0: what was chosen, what was rejected, and the
trigger — the observable condition under which a decision is reopened. Where a
measurement settled a decision, it sits inside that decision rather than in a
list of its own. Some decisions changed during the version; they keep their
history, marked *revisited* or *reversed*, because the reason a decision
changed is part of the reason it holds now. *Calibrated* means that the tests
claiming to protect a decision were checked by breaking it on purpose and
watching them fail.

What changed in the code is in the [changelog](../../CHANGELOG.md); what is
known and still open is in [known gaps](../known-gaps.md).

## Provider access and the client

- **Provider transport (measured, revisited).** The original choice was a
  direct connection to `api.anthropic.com`, with aggregators rejected on the
  grounds that two stacked abstraction layers make it impossible to tell whose
  behaviour is being observed. That decision was reopened against its own
  written trigger — a real access barrier — when the provider console proved
  closed to new accounts. Requests now route through an Anthropic-compatible
  gateway via `llm_base_url`, using `auth_token` (Bearer) rather than `api_key`
  (`x-api-key`). The concern behind the original rejection is now an observed
  cost: the gateway balances requests across upstream providers — the recorded
  response was served by Amazon Bedrock — so what is observed through it is the
  gateway together with whichever provider answered. Both paths speak the same
  API, Anthropic's Messages format, so the route is a deployment setting, and
  what the code is tied to is that API, on either route. The trigger to revisit
  is direct provider access becoming available; `llm_base_url` defaults to
  `None`, so returning to the direct path is a `.env` change, not a code
  change. The direct path has not yet run against the provider's own API (see
  known gaps).
- **Gateway model identifiers are not provider-native.** The compatibility
  endpoint is wire-compatible on request and response shape but resolves model
  names against its own catalogue: the provider-native id
  (`claude-haiku-4-5-20251001`) returns `404`, and the gateway form
  (`anthropic/claude-haiku-4.5`) is required. Because model choice lives in
  configuration rather than in code, this was a one-line `.env` change.
- **The SDK's defaults were confirmed against its documentation, not inferred
  from one run.** Observed `max_retries=2` and a 600-second default timeout
  match the published SDK behaviour. The agreement matters: a single
  observation through a gateway could have reflected an overridden value, and
  the retry budget depends on knowing which of the two is true.
- **The SDK's own retry policy is switched off (`max_retries=0`).** Left at its
  default of 2, it would multiply with the application's retry layer rather
  than add to it — a three-attempt budget becoming nine billed calls. It was
  switched off before that layer existed, because the multiplication would
  otherwise have surfaced in a file that does not mention retries.
- **No SDK type crosses the boundary.** Seven fields leave `app/core/llm.py`:
  text, stop, `input_tokens`, `output_tokens`, model and, added with usage
  accounting, `elapsed_seconds` and `reported_cost_usd`. Of the fields only the
  gateway sends — `cost`, `cost_details`, `is_byok` and `speed` inside `usage`,
  and `provider` at the top level — only `cost` crosses, as the optional
  `reported_cost_usd` (see Usage accounting); code reading the others would
  break silently the day direct access is restored. The response `id` is
  excluded too. Its format depends on who answered — `gen-…` in an early
  gateway response, `msg_bdrk_…` in the recorded one — and the usage records
  correlate attempts by a request id the service generates, so the provider's
  id has no consumer. No `ABC` or `Protocol` is introduced: with a single
  implementation, an interface can only be a copy of that implementation's
  signature. Trigger: a second provider actually being connected.
- **The error type carries data, not just a message.** `LLMError` holds the
  provider's status code and the provider exception's *type name* as a string.
  Without them, the error taxonomy would have to either import the SDK to catch
  its exception classes — defeating the boundary — or parse error text. The
  message itself is a fixed string: SDK errors can attach the request body, and
  that body holds prompts and, later, retrieved context. `getattr` is used for
  the status code because connection and timeout errors do not carry one.
- **Stop reasons are mapped into this project's vocabulary, with a fallback.**
  The provider's strings are confined to a lookup table, and an unrecognised
  value resolves to `UNKNOWN` instead of raising — a unilateral addition on the
  provider's side should not break working code. `stop_sequence` is folded into
  `COMPLETED` because no stop sequence is configured; trigger to split it: one
  actually being passed. Of the seven values the pinned SDK declares, four were
  mapped at first and the rest fell to `UNKNOWN`, which was correct while
  nothing consumed them. `refusal` and `model_context_window_exceeded` gained
  their own members, `REFUSED` and `CONTEXT_OVERFLOW`, when structured output
  gave them a consumer: a parse failure then had three candidate causes, and
  two of them were sitting in the same information-free bucket.
- **The model identifier is read from the response, not from the request.** The
  gateway resolves model names against its own catalogue, so the configured
  value and the value actually used need not match. The usage records keep the
  model that was used, not the one that was asked for.
- **Translation is a module-level function (revisited).** `to_completion` is a
  function rather than a method, so it can be exercised without constructing a
  client or reaching the network. Testing the client through a mocked HTTP
  transport was rejected at first: the client did nothing beyond one call and a
  translation, and such tests bind to wire JSON. Its trigger — the client
  acquiring behaviour beyond that — fired with provider-error translation, and
  the client is now also tested beneath a real SDK client over a mocked
  transport (see Testing).
- **The client owns its transport and releases it.** `LLMClient.aclose()`
  closes the SDK client, whose HTTP connection pool holds sockets and TLS
  sessions — operating-system resources, which garbage collection does not
  reclaim. The embedding model's pattern did not carry over: it had nothing to
  close. The wrapper keeps the `aclose()` name because the `a` prefix marks a
  coroutine for this project's callers; the SDK calls its method `close()`.
  That difference was found by failure: the first version called `aclose()` on
  the SDK client, which does not have it, so every shutdown raised
  `AttributeError` from the first statement of the lifespan's `finally` block,
  the `pool.close()` below it never ran, and the database pool leaked.
- **The client is application-scoped.** `get_llm_client` reads it from
  `app.state` instead of building one per request: an object holding a
  connection pool is application-scoped for the same reason the database pool
  is. The lifespan acquires the pool, the embedding model and the client inside
  one `try`/`finally`, and closes the client and the pool in reverse order.
  Once there were two closeable resources, failing to acquire the second would
  have leaked the first, and a teardown that read `app.state` raised on a path
  where the attribute had never been set.
- **The factory takes the HTTP client it sends through.**
  `create_llm_client(http_client=...)` hands an `httpx.AsyncClient` to the SDK
  on both paths; the application passes none, and the SDK builds its own. It
  exists so that the response-variability measurement can see the bytes the
  gateway sent while going through the production factory. A script building
  its own SDK client was rejected: it could copy the gateway/direct branch
  wrongly and record the wrong path's response, and the probes that had done so
  left out `max_retries=0` or the phase timeouts. Reaching into the SDK
  client's private attributes was rejected too. The SDK sets the factory's
  timeouts on every request it builds, so a supplied client keeps them. A test
  passes a recording client on both paths; removing the argument from one
  branch was checked to fail that branch's case only. Trigger: production
  itself needing to pass a client, such as for tracing.

## Prompts

- **Template engine: Jinja2, configured with `StrictUndefined`.** Two
  constraints drove the choice: prompts carry literal braces (the
  structured-output prompt shows a JSON example), and a missing variable must
  be loud. `str.format` was rejected because escaping every brace stops the
  file from being plain text a human can copy into a playground — defeating the
  reason for putting prompts on disk at all. `string.Template` satisfies both
  constraints with zero dependencies and was the initial choice; it was
  reversed because it forces a planned engine migration once a prompt needs
  iteration, and the roughly half hour it saved did not cover that. Jinja2's
  unused loop support costs nothing: an unused capability inside a dependency
  carries no maintenance, unlike an unused abstraction one writes oneself.
- **Jinja2 is a direct dependency.** It was already in the lockfile as a
  transitive dependency of `torch`; relying on that would break the prompt
  layer at import the day the embedding stack leaves the image.
- **Both directions of variable mismatch are errors.** A declared variable the
  caller omitted, and a supplied variable the template never declared, both
  raise. The second is the one no library catches: Jinja2 silently ignores
  extra keys, so the caller believes data was injected, the data never reaches
  the prompt, the model answers fluently from a partial input, and the call is
  billed. Mutation testing confirmed the asymmetry — removing the
  missing-variable check still fails loudly via `StrictUndefined` (with a worse
  message), while removing the extra-variable check produces no error at all.
- **Errors carry the prompt identifier.** Jinja2's `UndefinedError` names the
  variable but not which prompt or which version failed; that information
  exists only in the registry. Two types, split by who can catch them: load
  failures happen at import and stop the process before anything can handle
  them, render failures happen in front of a caller.
- **The version lives in the filename** (`<name>.v<N>.txt`), parsed into a name
  and an integer at load time. An integer rather than semver, because a prompt
  has no API surface for compatibility to describe; all a version has to
  express is order. In the filename rather than in file-internal metadata,
  because a frontmatter version can drift from the filename and nobody notices.
  A filename that does not match the pattern is an error, not a skipped file —
  skipping would hide the prompt's existence until something asked for it and
  got "not found". The usage records store the identifier as written
  (`extract_paper_facts.v1`), so a query that orders by version has to read the
  integer back out of it (see known gaps).
- **Templates load once, at import, with no wiring.** The path resolves against
  the module's own location rather than the working directory, unlike
  `scripts/migrate.py`. Nothing is placed on `app.state` and no dependency
  accessor exists: that pattern is for resources that are expensive or need
  closing, and a few KB of text is neither. Eager loading buys fail-fast for
  free — a malformed template raises during import, so `uvicorn` never starts,
  rather than surfacing on the first request.
- **One file per prompt, with named sections.** `user` is required, `system`
  optional and rendered as `None` when absent, matching
  `complete(system=None)`. Two files per prompt were rejected because nothing
  forces them to move together across a version bump. TOML and YAML were
  rejected not because they cannot hold the text — a YAML block scalar can —
  but because they add a parser's worth of failure surface and stop the file
  from being plain text.
- **Template variables use the prompt's vocabulary, not the database's.** The
  templates say `abstract` where the column says `summary`; mapping the two is
  the calling service's job, and the service tests pin which column fills which
  variable.
- **Calibrated.** All three checks were verified by mutation. Removing the
  missing-variable check left one test red on the error message rather than the
  exception type; removing the extra-variable check left one test red with
  nothing raised at all. Removing `StrictUndefined` broke nothing, because the
  registry's own check runs first and shadows it; what `StrictUndefined` alone
  guards, a missing attribute on a supplied object, no template uses (see known
  gaps).

## Structured output

- **Output contracts live in `app/generation/`.** The package holds what a
  provider's output is validated against, so parsing can be exercised with no
  database, network or client. `app/schemas/` was rejected: that package is the
  HTTP contract, and a model validated against a provider's output does not
  live at the HTTP boundary. A separate errors package was rejected too — in
  this project a domain error type lives in the module that raises it, as
  `LLMError` and `PromptRenderError` do.
- **Native structured output (measured, reversed).** The initial decision was
  to rely on prompt instructions alone and validate locally, on three grounds:
  gateway support was unverified, using it would widen the client's signature,
  and its only benefit — a lower validation-failure rate — had never been
  measured. All three were tested. The gateway accepts `output_config`. The
  failure rate was measured on a fixed input with the decision rule written
  first (`scripts/measure_json_compliance.py`, three runs of ten per arm):
  **prompt-only produced directly parseable JSON 0 times in 30, `output_config`
  30 times in 30.** Every prompt-only failure had the same shape — the model
  wrapped its JSON in a markdown fence, despite the prompt forbidding it in
  those words. A prompt instruction is a soft constraint competing with a
  formatting prior, not a rule. Stripping the fence in code was the third
  option and was rejected: it is correct only as long as one can enumerate the
  shapes a model might emit, and `{fence: 30}` is an observation about today's
  model, not a contract. Migration cost was at its lowest: `complete()` had no
  caller yet, so nothing broke.
- **Local validation stays regardless.** Zero failures in 30 calls does not
  bound the true failure rate near zero; with no failures in 10 trials the
  conservative upper bound on the failure rate is about 30%. No practical
  sample size would license removing the validation layer, which is why none
  was taken. Native constrains syntax; local validation is the contract, and
  the contract must not depend on a provider feature.
- **The schema crosses the boundary as a plain `dict`.** The caller supplies
  JSON Schema; wrapping it in the provider's envelope is the client's job.
  Accepting a Pydantic model class instead was rejected: the client would then
  have to know that a task has a response shape, which is the same leak the
  prompt boundary already avoids. The observable form of this decision:
  `output_config` appears in one source file under `app/`. The schema's source
  is the Pydantic model in `extraction.py`, and the service carries it to the
  client.
- **The schema is sent as Pydantic generates it (measured).** Input tokens per
  call: 247 with no schema, 449 with a hand-written schema (230 characters),
  500 with the schema Pydantic generates (284 characters). The 51-token
  difference is entirely `title` metadata Pydantic attaches to every field and
  to the model; it constrains nothing. It is not stripped: that requires a
  custom schema generator, and 51 tokens is not a measured cost problem. JSON
  is dense in tokens — 284 characters cost 253, roughly 3.5 times the
  token-per-character rate of prose, because its punctuation tokenises badly.
  The gateway accepted the schema without `additionalProperties` 10 times in
  10; some providers' strict modes require it, this one does not. The schema
  costs money, not time: in an interleaved run the median latency of both arms
  was 1.76s, although the schema arm sent 253 more input tokens per call —
  input tokens are processed in parallel and output tokens one after another,
  so a larger prompt buys a larger bill rather than a slower call. An earlier
  6.5x gap between the arms came from running them in blocks and did not
  survive interleaving. Trigger: the schema growing in v5. The other half of
  the original trigger, the schema's share showing up in the usage accounting,
  cannot fire: the records keep input tokens per attempt, not the schema's
  share of them.
- **The extraction prompt describes the fields; it does not embed the schema.**
  `extract_paper_facts.v1` describes three fields in prose and shows one
  compact example object. The schema already travels as a request parameter,
  and carrying it in the prompt too would pay for it twice. The three fields
  have three different types, the smallest set that exercises three separate
  validation paths.
- **Structured answers arrive as one text block.** `to_completion` joins a
  response's text blocks and ignores the rest. In the compliance runs both arms
  returned a single `text` block, so the concern that a structured answer might
  arrive in a non-text block does not apply on this path.
- **One error type, carrying a discriminator.** Unparseable text and a schema
  violation occupy the same position in the error taxonomy — neither is
  retryable and the caller behaves identically — so two types would be a split
  with no consumer. Collapsing the *types* is not collapsing the *information*:
  `ExtractionErrorCause` distinguishes the two cases, in this project's
  vocabulary rather than Pydantic's. Naming the cause `json_invalid` after
  Pydantic's internal error string was rejected for the same reason provider
  stop reasons are mapped rather than passed through — a library upgrade would
  then change a domain contract.
- **The error carries no model output.** Pydantic's `errors()` entries include
  an `input` key holding the value that failed, and `str()` on a
  `ValidationError` embeds it for some error types but not others. Only `type`,
  `loc` and `msg` are copied, by allow-list rather than by deleting `input` — a
  deny-list silently leaks the day the library adds a field. Measured: with the
  canary in the field that fails validation, removing both defences leaves the
  leak test red; with the canary in any other field the same mutation passes
  all three tests.
- **Field names belong to the prompt's vocabulary, not the database's.** As
  with template variables, mapping is the calling service's job. The schema is
  kept minimal — every field is one more thing the model must get right and one
  more way validation can fail. A `reasoning` field, which gives a constrained
  model somewhere to think before committing to values, was considered and
  deferred: its benefit is unmeasured here, and it is reassessed together with
  any future change to the constraint decision.
- **No repair layer, no retry on validation failure.** The scope is to
  validate, not to repair, and a repair loop is a retry under another name —
  both calls are billed. Trigger: validation failures being seen in practice
  and repeatably.
- **Truncation diagnosis is not the parser's job.** `parse_paper_facts` takes a
  `str`, so it never sees `stop`. That keeps parsing independent of the client,
  and the cost is that "the JSON is incomplete because `max_tokens` cut it" can
  only be established by whoever holds the completion and the error at once —
  the service (see Generation).
- **Validation is structural, and no test pretends otherwise.**
  `tests/test_extraction.py` covers valid JSON, unparseable text, and JSON that
  parses but violates the schema. A case for output that satisfies the schema
  while being factually wrong is deliberately absent: this layer does not catch
  it, and testing for what a layer does not do misdescribes what the test
  protects. Faithfulness belongs to v6's evaluation.
- **Calibrated.** Each behaviour this layer claims to protect was verified by
  an isolating mutation. Widening the schema's field types to `Any` left
  exactly the schema-violation test red; forcing the error cause to a constant
  left exactly the unparseable test red; dropping `refusal` from the
  stop-reason table left exactly its translation test red; carrying Pydantic's
  raw error entries left exactly the leak test red. A coarser mutation —
  replacing validation with a bare `json.loads` — turned all three extraction
  tests red and proved only that each protects *something*; how many tests a
  mutation reddens is not a measure of its value.

## Generation

- **Generation has its own service.** `GenerationService` is the first
  orchestration layer over a dependency that is non-deterministic, billed per
  call and able to fail partially. It was not folded into `ArticleService`:
  semantic search had joined that service because it shared its repository and
  the `RetrievalResult` contract, and generation shares neither.
- **The caller selects the document.** A use case takes one article by primary
  key. A system that selects the documents itself, by retrieval, is v5.
- **The endpoint is `POST`, not `GET`.** The call has a side effect — it spends
  money — and is not idempotent: the same request produces different output. A
  cacheable, safe method should claim neither.
- **No response streaming.** The whole answer is returned at once. Trigger:
  several sequential LLM calls for one request, total durations regularly above
  15 seconds, or a human interface waiting on the answer.
- **What a use case sends is a value.** Each use case's request — messages,
  system prompt, `max_tokens`, schema, and the prompt identifier it is recorded
  under — is a `GenerationRequest`, built by a function that does no I/O:
  `extraction_request` or `summary_request`. `_generate` only sends it. The
  request used to be assembled in two places inside the service, so code
  outside the service could send it only by copying it, and three consumers
  need it: the service, the response-variability measurement and the live test.
  A copy in the measurement would calibrate a request production does not send;
  a different `max_tokens` there would silently void the truncation evidence.
  What is sent is separated from how it is sent — retried, observed, recorded —
  a small instance of functional core, imperative shell.
  `to_completion_kwargs()` names the one field that must not be sent rather
  than listing those that must: a new field reaches `complete()` without anyone
  adding it, and a field that should stay on this side fails loudly, because
  `complete()` rejects an argument it does not declare. The builders share a
  private helper with typed keyword arguments rather than a partial dict,
  because the model ignores unknown keys by default and a misspelled optional
  key would be dropped without a word. Before the refactor, two
  characterization tests pinned the exact request each use case sends, and they
  passed against the old code first. Rejected: a copy of the request in each
  consumer with a test comparing it to the service's, which adds two artefacts
  and leaves the script's copy unchecked; and keeping the live test at the
  service level so that it sends the real request (see Testing). Trigger: a
  request that stops being one value, such as a use case whose calls depend on
  each other's answers.
- **The stop reason is a precondition, not an explanation.** The service checks
  `stop` before it calls the parser, rather than reading it to explain a
  failure the parser already reported. Two measured facts drive the ordering:
  constrained decoding guarantees syntax but not completion, so a truncation
  landing after the closing brace parses cleanly and a parse-first ordering
  accepts it silently; and a refusal returns prose, which parse-first would
  report as unparseable output — technically true, diagnostically wrong. The
  test that separates the two orderings feeds a truncated stop reason together
  with *valid* JSON; with malformed JSON both orderings fail and the test
  proves nothing.
- **An article with no usable abstract is rejected before the request is
  sent.** Rendering a null value is silent — the template engine's
  strict-undefined mode fires on missing variables, not on `None`, and puts the
  literal string in the prompt. The response built from it satisfies the
  schema, so no downstream layer catches it. Substituting an empty string, as
  the embedding pipeline does for the same column, was rejected: the pattern
  transfers but its conclusion does not, because that path costs CPU and this
  one costs a billed call plus a persisted invention.
- **Two error types, split by when they occur rather than by what caused
  them.** `NoSummaryError` is raised before any provider call and carries no
  token cost; `GenerationError` is raised after one and always does. That
  boundary is what the retry budget and the usage accounting each rely on: a
  `NoSummaryError` leaves no attempt to record, and a `GenerationError` always
  comes after one. `GenerationError` carries the stop reason as data rather
  than folding four situations into one message — truncation is retryable with
  a different token limit, a refusal is not retryable at all, and a context
  overflow is not retryable without shrinking the input. Same rule as the error
  types before it: the type carries data, so the layer above classifies without
  importing anything or parsing a string. The message is a fixed string.
- **The second use case shares preparation, not validation.** Fetching, the
  empty-abstract check and rendering became shared once a second method needed
  all three; the structured path keeps its schema and its parser, and the
  free-text path has neither. The stop check is shared, because an incomplete
  generation is unusable regardless of the output shape. `summarize_article`
  has no route yet (see known gaps).
- **`_generate` holds the mechanism; the public methods keep their decisions.**
  Finding the article and accepting and parsing the completion differ by use
  case; how a provider call is made — retried, observed, recorded — is the same
  for every use case and has one home. The prompt identifier is written once
  per use case, in its request builder, and feeds both the rendering and the
  record, so a row cannot name a prompt that was not sent.
- **The request id and the recorder belong to one call, not to the service.**
  One instance may serve several calls — FastAPI builds one per HTTP request,
  but tests and scripts need not — and a recorder kept on the instance would
  carry one call's attempts into the next call's rows, under the new id and
  prompt. The primary key would not catch it.

## Errors and HTTP mapping

- **Every application error derives from `AppError` and carries a category.**
  `AppError` and `FailureCategory` live in `app/core/errors.py`, which holds
  vocabulary only — no HTTP, no provider names, no import from an upper layer —
  so a single handler registration catches every error through the MRO walk.
  Classification is carried on the error type, not looked up in a central
  table: a table would let a newly added type fall through to a default while
  nothing complained, whereas a required keyword-only constructor argument
  means a type that supplies no category cannot be constructed at all. The
  enforcement is the signature, so no `__init_subclass__` check was written: a
  mechanism was drafted twice and both drafts leaked — the first through
  `hasattr` walking the MRO, the second through an `is_abstract` escape hatch
  that is itself inherited. Inheriting the field is allowed: `PromptError`
  declares a category and both its subtypes inherit it.
- **One handler, registered on the base type.** Because classification is data,
  the handler body does not branch on the concrete type; per-type registration
  would register the same function eight times and force
  `app/core/exceptions.py` to import four upper-layer modules, breaking a
  direction rule that has held since v2. Handler lookup walks
  `type(exc).__mro__`: a handler on a base type catches every descendant, and
  when both a base and a child are registered the child wins regardless of
  registration order — verified by running both orderings; `HTTPException` is
  resolved by integer status code first, ahead of the walk. `_CATEGORY_CONFIG`
  maps each category to a status code and a log level and is read by direct
  indexing, so a category missing from it fails loudly rather than defaulting.
  Trigger: one type needing HTTP behaviour different from its category's — the
  MRO walk resolves a specific registration ahead of the base one.
- **HTTP status is not a field on the error type.** Error types carry a
  category in our own vocabulary; the translation to a status code happens only
  at the outermost layer. A status on the type would make a retry loop or a
  background worker — neither of them HTTP consumers — carry HTTP vocabulary.
- **No `retryable` field.** Across all thirteen failure modes, retryability is
  `category is UPSTREAM_UNAVAILABLE`; a second hand-declared field is a second
  field that can contradict the first. Trigger: a mode becoming retryable
  without being upstream-unavailable — the two known candidates are a
  truncation retried with a larger `max_tokens` and a schema violation retried
  against non-deterministic sampling, and both already have their own triggers.
- **Two messages, two audiences.** An error's message goes to the log and may
  name templates, models or internal state; `public_message` crosses the
  network and holds fixed text plus, at most, values the caller supplied in the
  request itself. The rule was first written as "never interpolates anything"
  and relaxed deliberately when the 404 body had to keep naming the requested
  id: a value that arrived in the caller's own URL is not a leak; a provider
  response, model output or piece of internal state still is. `log_context()`
  adds the discriminating fields a fixed message cannot carry: `LLMError` its
  status and provider error type, and `retry_after` only when the provider sent
  one, since an unconditional key would put `retry_after=None` on every error
  line; `GenerationError` its stop reason; `ExtractionValidationError` its
  cause. The types whose message already carries the detail return nothing.
- **Domain errors are logged without a traceback; unclassified ones keep
  theirs.** The exception chain carries what the error types were built to
  withhold: a chained `ValidationError` prints the rejected value in
  `input_value`, and an SDK error's message embeds the provider's full response
  body. The allow-list protects the error object, not Python's chain. A genuine
  bug has no structured fields, so for it the traceback is the only evidence —
  and the server prints it. `Starlette.build_middleware_stack` routes a handler
  registered for `500` or bare `Exception` to `ServerErrorMiddleware`, which
  sends its response and then re-raises unconditionally, and every other
  handler to `ExceptionMiddleware`, which does not re-raise when a handler is
  found. `handle_unexpected_error` therefore logs one line without the
  traceback: its own copy had been the second one.
- **Structured fields go into the message, not into `extra=`.** Passing them
  through `logging`'s `extra` parameter sets attributes on the record, and the
  formatter — `%(asctime)s - %(levelname)s - %(message)s` — never reads them:
  nothing is printed and nothing warns. Fields go into the message through
  `%`-args, as `key=value`.
- **The category comes from the status code, not from the SDK's exception
  class.** The SDK's `_make_status_error` maps 400, 401, 403, 404, 409, 413,
  422, 429 and 529 to their own classes and everything else above 500 to one.
  `ServiceUnavailable` and `DeadlineExceeded` exist as classes, but this code
  path never produces them, so 500, 502, 503 and 504 share a class name and
  only the number tells them apart.
- **`handle_database_error` left as it is.** The concrete reason to touch it
  was a reported leak of connection parameters; the leak could not be
  reproduced, and a failed connection raises `ConnectionRefusedError`, which is
  not a `PostgresError` and never reaches that handler. Trigger: a leak
  observed on the `PostgresError` path.
- **Not found joined the taxonomy (revisited).** At first the service returned
  `None` and the router raised the HTTP error, as the article endpoint already
  did: an exception handler binds to an exception type and cannot bind to a
  return value. The question was reopened when the domain-error handlers were
  built. An endpoint's success/failure line follows the contract it declares,
  not how ordinary the event is: `POST /facts` promises a `PaperFacts` object,
  and a missing article means it cannot be produced — the same reasoning
  already applied to a model refusal. Keeping the return value kept status
  codes defined in two places, so the handler was not the single source of the
  set an API can return. `NotFoundError` needed three exceptions to the rules
  the other categories follow: `INFO` rather than `WARNING`/`ERROR`, an
  interpolated public message rather than a fixed literal, and a home in
  `errors.py` rather than in the module that raises it — a missing resource
  belongs to any lookup, and two services raise it, so defining it in either
  would make one service import the other. `GET /articles/{arxiv_id}` followed,
  so the application has one 404 mechanism. Trigger: a fourth exception to the
  category rules.
- **The declared status set is kept by hand.** Three places say which statuses
  `POST /articles/{arxiv_id}/facts` can return — the route's `responses`,
  `_CATEGORY_CONFIG` and the README's API table — and they agreed when checked
  at the version close. No test ties them together, because nothing reads the
  OpenAPI document. Trigger: a client generated from the OpenAPI document.
- **`RetryableError` and `WorkloadIdentityError` are out of scope because they
  are unreachable, not because they are unlikely.** `RetryableError` is an
  input to the SDK's retry policy — something middleware raises to request a
  retry — and the SDK never raises it; `WorkloadIdentityError` comes only from
  the workload-identity credential providers, which a plain `api_key` never
  engages. An earlier note describing the first as a gap in `except
  anthropic.APIError` was a reachability error.

## Retries and timeouts

- **One retry layer, owned by the service's call site.** The loop lives in
  `app/core/retry.py`, and the service wraps only the provider call: the record
  is read and the prompt rendered once, so every attempt repeats the same
  request. Rejected: a loop inside `complete()`, which would break the
  single-call invariant the attempt budget rests on; and a retrying wrapper
  installed in the lifespan, whose one line of wiring no test runs and which
  would hide attempts from the layer that records their usage. Installed in the
  factory instead, it would also change what
  `scripts/measure_json_compliance.py` measures. Trigger for centralising: a
  second service that calls the provider.
- **The switched-off SDK policy, restored element by element.** Kept: three
  attempts, a 0.5s base doubling per retry, a wait trimmed by at most a quarter
  (a 75% floor suits a single caller better than full jitter, which can fall to
  zero), and `Retry-After` honoured up to 60s. Changed: a longer `Retry-After`
  ends the retrying, where the SDK falls back to its own backoff and tries
  sooner than asked; the gateway's documentation asks for the header to be
  honoured. Dropped: retrying 408 and 409, which the error taxonomy classifies
  as internal; `x-should-retry`, not observed through the gateway; and the 8s
  cap, which three attempts never reach. The requested wait crosses the client
  boundary as seconds, read from `retry-after-ms` first and `retry-after`
  second; only numbers are read, and a value that is negative, not finite or a
  date counts as absent. Every value is borrowed from the SDK, not measured
  here; the per-attempt records are the first data to tune them, and nothing
  has been tuned from them yet.
- **The policy is pure; the wait and the random draw are injected.**
  `plan_retry` and `backoff_delay` hold the policy as functions, and
  `Retrier.run` takes a factory for the provider call, because a coroutine can
  be awaited only once and each attempt needs a new one. Tests observe every
  wait without waiting. Each retry logs one `WARNING` in the same `key=value`
  shape as the HTTP error handler, because a retry that ends in success leaves
  no other trace that the upstream faltered.
- **A request that timed out is retried.** The provider may already have billed
  it — the gateway documents that cancelling a non-streaming request still
  bills the full response — but `max_tokens` caps that cost at about $0.003 per
  attempt at the provider's list price, the gateway's margin excluded. The
  decision holds only while the read bound sits well above the longest
  generation `max_tokens` allows; otherwise a slow input times out on every
  attempt, and retrying pays three times for nothing. Trigger: a larger
  `max_tokens`, or records showing one request timing out on every attempt.
- **No deadline on the whole request.** A hard deadline cancels an attempt in
  flight, and on this path cancellation saves no money and throws away a result
  already paid for; the trickling response it would bound has not been
  observed. A soft budget — no new wait or attempt once time runs short — is
  deferred, because its value depends on whether a retry after a timeout ever
  succeeds, and nothing has measured that. The rule is written before the data:
  if retried requests outlast one attempt's ceiling of about 35s, set the
  budget to about 60s when retries after a timeout rarely succeed, which allows
  none, or to at least 66s when they do, which allows one. Until then the worst
  case is about 107s through timeouts and about 157s through two maximal
  `Retry-After` waits, absent a trickling response.
- **The service builds its own retrier.** A constructor parameter was planned
  so tests could inject a fake sleep. A zero `Retry-After` makes the shipped
  retrier retry at once, so the tests exercise the wiring as it ships and the
  parameter would have no consumer. Trigger: a caller that needs a different
  policy, such as a background worker.
- **The retry layer is typed to `LLMError`.** It is the only error that can be
  `UPSTREAM_UNAVAILABLE` and the only one with a `retry_after`; a loop typed to
  `AppError` would need `getattr` on a field the base type does not declare.
  Trigger: a second error type that can be `UPSTREAM_UNAVAILABLE`.
- **Retries do not fire the streaming trigger.** Its first condition names
  several sequential calls per request, meaning a pipeline of different calls
  whose latencies add up for a waiting reader. A retry repeats one call, and
  streaming a failed attempt gains nothing. Its second condition says
  *regularly*, and retries are the exception.
- **Each phase has its own timeout (measured).** `create_llm_client` builds an
  `httpx.Timeout` rather than passing one float. The float set all four phases
  to the same value and lifted the connect bound from the SDK's 5s; connection
  setup now has its own 5s bound, and `LLM_TIMEOUT_SECONDS` bounds the read,
  write and pool phases. Its meaning narrowed with it — an idle limit per
  phase, not a limit on the call. Measured over a real socket, with the
  client's timeout set to 2s: a response that sent one byte per second for six
  seconds returned `200` after 6.04s; headers at 1.5s and the body 1.5s later
  returned `200` after 3.01s; a single 2.6s silence raised a read timeout at
  2.01s. Even without a trickle, headers and body are separate reads, so one
  attempt can last close to twice the bound.
- **The timeout values are borrowed, not measured.** A 12.34s figure once
  recorded as a single call was an arm mean: one blocked arm of ten averaged
  12.34s, and the same configuration, re-run, averaged 1.65s. The longest
  single call has not been recorded anywhere, and a ten-call run in calm
  conditions reports a calm maximum, so the tail will come from
  `llm_attempts.elapsed_seconds` rather than from any one run.

## Usage accounting

- **Cost is the figure the gateway reports (reversed).** Gateway responses
  carry fields the provider's own API does not, `cost` among them. The original
  decision was not to trust them, because they disappear on the direct path,
  and to compute cost from `input_tokens` and `output_tokens` against a price
  model of our own. It was reversed when the usage records were designed: each
  attempt record keeps the cost the gateway reports, as `reported_cost_usd`,
  and leaves it empty on the direct path. A price model would be a second
  source of truth, maintained by hand and silently wrong the first time a price
  changed, and it would only estimate a figure the gateway already states for
  the call. The direct path loses nothing it had: tokens are recorded on both
  paths, so a price model can still be applied to any row later. Measured: the
  first live record — one `POST /articles/{arxiv_id}/facts` through the
  gateway, 644 input and 161 output tokens, 4.90s, model
  `anthropic/claude-haiku-4.5` — reported $0.001449, and at the provider's list
  price for Claude Haiku 4.5, $1 per million input tokens and $5 per million
  output tokens, the same tokens cost $0.000644 + $0.000805 = $0.001449. The
  reported model matched the configured one, and a request for an unknown
  article left no row. Later, all 31 calls of the response-variability
  measurement matched list price times their tokens exactly, and in the
  recorded response `cost` equals `cost_details.upstream_inference_cost`: no
  margin on the call itself is visible. Trigger: a consumer that needs a cost
  on the direct path, or a reported cost that disagrees with list price times
  the recorded tokens.
- **A malformed cost never fails a paid call.** `parse_reported_cost` reads the
  SDK's undeclared `usage.cost`. Anything that is not a usable price — absent,
  not a number, a boolean, negative, not finite, too large for a float —
  becomes `None`, and parsing never raises: a malformed accounting field must
  not fail a call that has already succeeded and been paid for. `None` means
  unknown, not free. Because the parser is silent, only a live call can notice
  the gateway dropping the field (see Testing).
- **Every call is timed, with an injected monotonic clock.** Every provider
  call is timed inside `LLMClient.complete()`, on success and on failure, with
  a clock that defaults to `time.perf_counter`. Only the difference between two
  readings is used, so the clock must be monotonic, which `time.time` is not.
- **Input tokenisation is deterministic, sampling is not (measured).** Input
  token counts were identical across every call in every run — 500 in all 31
  calls of the response-variability measurement — while output counts were not.
  A cost estimated before a call can be exact on the input side and only on the
  input side; the records keep what each call used rather than predicting it.
- **The unit of record is the attempt, not the request.** A retried request
  makes several provider attempts and any of them may have been billed — a
  timed-out call included — so recording only the request, or only its last
  attempt, would hide exactly the cost a retry adds. The design criterion was
  that "how many attempts did this request take, and what did they cost?" can
  be answered from the records, and one query over `llm_attempts` does (README,
  Usage Accounting). Rows are keyed by `(request_id, attempt)`; the request id
  is a `uuid4` the service generates for each logical request. Rejected:
  separate request and attempt tables, while nothing describes a request beyond
  its attempts; one row per request with aggregate counters, which cannot say
  which attempt cost what; and structured logs alone, which cannot answer the
  criterion with a query. Trigger: a v6 tracing backend that carries these
  fields end to end.
- **One table, and the outcome says what an empty column means.** A response, a
  translated provider error and an unclassified exception share `llm_attempts`,
  told apart by `outcome`. Empty means unknown or not applicable, and the
  outcome decides which: a response has no status code to report, while a
  failed attempt's tokens are unknown, not zero.
- **No `ON CONFLICT`.** Writing a request's attempts twice is a bug; the
  primary key refuses the second write instead of letting its cost be counted
  twice. It cannot see one attempt written under two request ids — that is the
  service's to prevent, and a service test holds it.
- **One `executemany` per request, after the request ends (measured).** One
  call is all-or-nothing on a pool and on a connection alike, so a request is
  never left half recorded. Writing each attempt as it happened would put a
  database round trip between retries and could leave a partial request behind.
  Measured: with `executemany` replaced by one `execute` per row, a batch
  refused at its third row left its first two rows committed; with
  `executemany`, none. The cost is that the attempts wait in memory until the
  request ends (see known gaps).
- **The records are written whatever the outcome.** The write sits in
  `finally`, so a request whose retries ran out — billed, perhaps, with nothing
  to show for it — is recorded like any other. A write placed after the call
  returns would lose exactly those attempts.
- **A failed write never changes the outcome (fail-open, measured).** By the
  time the write runs, the provider calls are over and the caller's result is
  settled. An exception raised in `finally` replaces it. Measured over HTTP,
  with the usage store refusing every write: with the fail-open `except`, a
  successful call answered `200` with its facts and an exhausted retry answered
  `503`; without it, both answered `500` with "Database service is currently
  unavailable" — a paid-for answer lost, and an upstream failure blamed on the
  database. The failure goes to an `ERROR` line carrying the records, so the
  loss is visible and recoverable rather than silent. `Exception` is caught,
  not `BaseException`: a cancellation is not a failed write and keeps
  propagating.
- **The recorder is transparent.** `observe` re-raises the original exception
  with a bare `raise`: the retrier reads its category and `retry_after`, and
  the HTTP layer picks a handler by its type, so a wrapped exception would turn
  a `503` into a `500` (measured). It catches `Exception`, not `BaseException`,
  because nothing in the application cancels an attempt yet. Trigger: the first
  change that does, such as a deadline, needs its own branch — a cancelled
  attempt may still have been billed.
- **`009` has no `IF NOT EXISTS`.** On a database whose schema already holds
  the table but whose ledger does not, `IF NOT EXISTS` would skip the statement
  with a notice nobody sees and record the migration as applied, hiding the
  drift. Without it the runner fails loudly and records nothing.
- **Schema changes go through `scripts/migrate.py` only.** The runner records
  each file in `schema_migrations` in the transaction that applies it; the
  files themselves are not re-runnable. A file run by hand changes the schema
  without the ledger, and the runner then fails trying to apply it again —
  which is how the working database had drifted, found when the runner, asked
  to apply `009`, stopped at `003`. It was repaired by recording the files
  already in the schema in the ledger, without running them.
- **Calibrated.** Every recording decision was broken on purpose. A recorder
  kept on the service, `observe` moved outside the retrier, the write moved out
  of `finally`, the fail-open `except` narrowed, the log call lowered to
  `DEBUG` or changed to `logger.error`: each failed exactly the tests that
  claim it. Removing the request id from the fail-open log line failed none
  (see known gaps).

## Testing

- **Doubles are hand-written, and grow only when a test needs them.**
  `FakeLLMClient` is a duck-typed stand-in that tracks `complete()`'s
  signature: if the two drift, a service that passes against the fake fails
  against the client, and the fake stops being evidence. It started with one
  canned response, no error mode and no call record, each to be added when a
  test required it. Call recording came with the service, because a canned
  response cannot show whether the service rendered the right prompt, mapped
  the right columns or passed the schema at all. A failure mode was declined
  when error translation was built — its trigger fired, but a double raising a
  hand-built `LLMError` would only have asserted what the test constructed —
  and arrived with the retry layer, the first code whose behaviour depends on
  what the client raises: the fake plays back a script of completions and
  exceptions, and a call past the end of the script fails the test, so an
  unplanned extra attempt cannot pass unseen.
- **The service tests use a real database and a faked provider.** The database
  is not replaced: the behaviour under test includes the repository query and
  the nullable column it returns. The provider is, because a real call is
  non-deterministic, billed and slow.
- **The provider-error translation is tested through the real SDK, not through
  `FakeLLMClient`.** The tests drive a real `AsyncAnthropic` over an
  `httpx.MockTransport`, so the SDK builds the request and maps the status to
  its own exception class exactly as in production, and only the socket is
  replaced. This also covers the branch where `status_code` is absent: a
  transport-level connection failure produces `APIConnectionError`, a class
  that has no such attribute at all.
- **HTTP-level tests arrived with the error handlers.** While the handler
  registered for bare `Exception` returned its response and then re-raised, the
  test client's default settings surfaced the exception instead of the `500`,
  so the first endpoint's paths were exercised by hand rather than pinned in a
  test the next change would rewrite. The first HTTP-level tests came with the
  category handler: the app is driven through `TestClient` with the service
  dependency overridden, so no lifespan runs and no database, model or network
  is touched. The `api_client` fixture imports `app.main` inside its body.
  Measured: of a 6.9-second warm run, 5.35s was collection and 1.55s execution;
  excluding `tests/test_service_article.py` — at the time the only test file
  that reached `sentence_transformers`, through `ArticleService` — dropped
  collection to 0.07s. The 28 database cases cost roughly 1.4s in total; a
  first cold run measured 23.85s and did not reproduce. At module level in
  `conftest.py`, the import would make every run pay that cost, including a run
  of one file that never touches the app. A full run pays it anyway:
  `tests/test_error_mapping.py` and `tests/test_router_articles.py` import the
  app at module level to override its dependencies, and
  `tests/test_service_article.py` reaches the model through `ArticleService`.
- **Route tests assert which service method ran, not the status code
  (measured).** A route can disappear without the URL going dark: with
  `/articles/search` deleted, the request matched `/articles/{arxiv_id}` and
  was served as a lookup for an article whose id is `search`. The status
  assertion passed on that path and only the call record caught it. Starlette
  tries routes in declaration order and the first match serves the request;
  `/articles/{arxiv_id}` matches any single segment, so the literal routes work
  only while they are declared above it, and reversing the two changes the
  answer with no warning at startup and no error at runtime. The same reasoning
  that put a `calls` list on the LLM double applies one layer up — when a wrong
  path can produce a right-looking result, the interaction is the evidence, not
  the outcome.
- **The router is tested for dispatch, not for existence.** An existence check
  — introspecting `app.routes`, or asserting the URL answers at all — passes in
  exactly the case that broke, because the catch-all answered. What needed
  holding still was the pairing between a URL and the method that serves it,
  and only a real request through the stack demonstrates it.
- **The search term stays a query parameter (measured).** Both shapes were
  compared across six query strings: `cs.AI/ML` answers `404` as `/search/{q}`
  and `200` as `/search?q=`, because `/` is a separator in a path and a value
  in a query string. `limit` and `offset` settle it independently — both carry
  defaults, and a path parameter cannot be omitted.
- **The batch test runs outside a transaction.** Inside one, the rollback that
  keeps the connection usable after the refused statement would also erase a
  half-written batch, so a half write and no write would look the same; a
  version built on a savepoint passed against a per-row implementation. The
  test writes through its own pool and deletes its rows in `finally`.
- **Service tests assert only what the service decides.** Which rows exist, how
  they group into requests, their numbering and their prompt belong to the
  service; token, model, cost and timing values belong to the recorder and the
  repository and are tested there. Expected values are literals, never the
  code's own enum values, and the exhausted-retry test's three failures carry
  distinct status codes, so each row can come from only one attempt. Rows are
  compared whole, after sorting where their order is not defined, so a failure
  shows the difference rather than `assert False`.
- **No separate test for a billed but unusable response.** The recorder test
  shows that a truncated response is recorded, and the exhausted-retry test
  shows that the service writes when a request fails; as long as the service
  does not filter records, the case is their composition. Trigger: the service
  filtering records.

### Testing a non-deterministic dependency

- **The model is not tested; the code around it is.** Three layers, each
  answering a question the others cannot. Hand-written doubles build any
  situation on demand — a `529`, a truncation, a malformed cost — that the real
  provider will not produce when asked. A recorded response checks, on every
  run and with a certain diagnosis, that the code reads what the provider
  actually sends. A live test checks, when asked, that the provider still
  behaves as the doubles assume. None of them judges the content of an answer;
  that is v6's evaluation.
- **Measured before asserting.** `scripts/measure_response_variability.py`
  sends the request `extract_facts` sends — built by `extraction_request`,
  through the production factory, with no `temperature`, as production sends it
  — thirty times, one after another, for one fixed article, and reports the
  values each field took. It works at `complete()`, so each call is seen on its
  own, without the retrier merging attempts or the service writing rows, and it
  keeps the text so that a parse failure can be named. N=30 follows from the
  claim it can support: with no event in 30 calls, the event's rate is below
  9.5% at 95% confidence; no N supports "never". Rejected: measuring through
  the service; and `temperature=0`, which would measure a request production
  does not send and would still guarantee no determinism. Trigger: a change of
  model, gateway or prompt.

The decision rule was written before the run and frozen. As written, translated
from the original:

> **Fields read:** `stop`, `text`, `input_tokens`, `output_tokens`, `model`,
> `reported_cost_usd`.
>
> **Expected guarantees:** `stop` is a string; `input_tokens` and
> `output_tokens` are integers, and `input_tokens` is always the same, because
> tokenisation is deterministic — the same text through the same tokenizer
> always gives the same tokens. Nothing else can be called guaranteed. `model`
> is a string; `reported_cost_usd` is a float, with no currency sign.
>
> **Model:** expected to be the same every time, but the gateway might change
> the model, and even thirty identical values would not prove that it never
> does. Assert equality only if the gateway's documentation shows the model is
> never changed, or that changing it can be switched off; otherwise assert only
> the type.
>
> **Outliers** in `reported_cost_usd` and `output_tokens`: not asserted; closer
> to a question of answer quality, for a later version if it proves useful.
>
> **`max_tokens`:** `output_tokens` above 500 should be impossible, but there
> is no evidence either way, so check the documentation. If `output_tokens`
> comes close to 500, raise `max_tokens`.
>
> **Assertions:** type and range (≥ 0) for `reported_cost_usd` and
> `output_tokens`; an exact value for `input_tokens`; `output_tokens` below
> `max_tokens`; only the string type for `stop` and `text`, since nothing about
> them is certain. Thirty identical observations are not a guarantee that the
> provider keeps a value constant.

The rule was then audited. Every assertion has to answer two questions — why
must this hold (a provider guarantee, or our own code depending on it), and who
relies on it — and none may restate what our own types or parsers already
enforce, because an assertion that cannot turn red protects nothing. The audit
changed the rule on principle, not because of a measured value; no assertion
was loosened to fit the run.

| Field | Rule as written | Live test asserts | Because |
| --- | --- | --- | --- |
| `stop` | a string | `== COMPLETED` | production's `_require_completed` depends on it; `stop` is our own enum, so its type cannot fail |
| `text` | a string | parses into `PaperFacts` | structured outputs guarantee that a completed answer fits the schema, refusals and `max_tokens` cut-offs aside, and production depends on it |
| `input_tokens` | the measured value | `> 0` | no code depends on the exact number, which moves with the template, the schema, the model and the provider; the offline request tests already pin the request |
| `output_tokens` | an integer, `≥ 0`, `< max_tokens` | `> 0` | the type is enforced by `LLMCompletion`, the bound by the provider, and a cut-off shows in `stop` |
| `model` | equal if guaranteed, else a string | nothing | the code only labels records with it; another model answering breaks nothing |
| `reported_cost_usd` | a float, `≥ 0` | not `None`, and `> 0` | the gateway documents usage accounting as always included, and the parser turns an unusable value into `None` without a word, so only a live call can notice; `≥ 0` could never fail, because the parser already enforces it |

Token counts above zero show that the provider reported the counts the records
store. Exact values belong to the offline recording test, where the input is
frozen.

- **What the run showed.** Thirty calls, after a one-call smoke run. Every call
  completed and every answer parsed, so truncation, refusal and an invalid
  answer each stay below 9.5% at 95% confidence. `input_tokens` was 500 in all
  31 calls. `output_tokens` ranged from 87 to 122 (median 103, 20 distinct
  values) against a `max_tokens` of 500 — about four times the largest — so
  `max_tokens=500` holds for extraction on this input; the margin is measured
  on one article, and the rule's own trigger stands: output tokens approaching
  the limit raise it. The cost was reported in every call, from $0.000935 to
  $0.00111. The model was `anthropic/claude-haiku-4.5` in every call. The
  recorded response names its upstream provider, Amazon Bedrock, at the top
  level of the body, not inside `usage`.
- **A recording is taken on the wire and never edited.** With `--record`, the
  script saves the first call that came back complete and parseable to
  `tests/recordings/extract_paper_facts.v1.json`: the article it asked about
  and the response body exactly as the gateway sent it, read by an `httpx`
  response hook below the SDK. Dumping the SDK's parsed `Message` was rejected:
  a body run through the SDK and dumped back gained ten keys the body did not
  have (`container`, `stop_details`, `stop_sequence` and seven under `usage`),
  so the dump describes the SDK's model, not the gateway's response. A
  recording is replaced by recording again, never edited by hand; taking it in
  the measuring script makes it one of the measured calls, reproducible with
  `-n 1 --record`. Trigger: a change of article, prompt version, model or
  gateway — measure again, then record again.
- **A recording is replayed beneath the SDK, and hand-written bodies stay
  (measured).** Two offline tests replay the recording through a real SDK
  client over a mocked transport, sending the request `extraction_request`
  builds for the recorded article. One compares the whole `LLMCompletion`,
  duration aside, with values read from the recording itself, so every field
  the project reads must come from where the gateway puts it, and a new
  recording needs no change to the test. The other parses the recorded answer
  into `PaperFacts` and checks that nothing is lost; it also notices a
  recording gone stale on this side, such as a change to `PaperFacts` the
  recorded answer no longer fits — the fix is a new recording. Replaying at the
  client seam was rejected: it would skip exactly the reading code the tests
  are for. The hand-written `RAW` body and its variants stay, because one
  recording is one situation, and it cannot tell apart two fields whose values
  happen to be equal. Measured: reading the cost from
  `cost_details.upstream_inference_cost` instead of `cost` passed the recording
  test — the two are equal in the recorded response — and was caught by the
  hand-written cost tests. Trigger: a second kind of recording.
- **The outgoing body is pinned offline.** Two tests read the JSON body the SDK
  sends. Given, an optional argument — `system`, `temperature`, the schema
  wrapped as `output_config` — appears in the shape the provider expects; not
  given, its key is absent rather than `null`, because an explicit `null` is
  not the same as an absent key and a provider may reject it. Only those keys
  are compared, so an SDK update that adds a key of its own does not turn the
  tests red. Before them, a regression in the request body could have been
  caught only by a live call, against the rule the layers rely on: offline red
  means our code, live red means the contract.
- **The live test is a contract test at the client.**
  `tests/test_live_extraction.py` sends the production extraction request once
  to the real gateway, through the production factory, for the measured article
  — the assertions were measured on that input, and another input would need
  its own measurement — and asserts the audited set, nothing about the answer's
  content. Its scope is the boundary with the one external service whose double
  the other tests rely on, so a red result means the provider side changed or a
  rare real event happened, while a regression in our code shows offline. The
  assertions run in the order that makes a red line say what happened — the
  stop reason first, because the schema guarantee holds only for a completed
  answer — and each carries a comment on where to look. A provider error fails
  the test rather than skipping it: a person runs it and reads the cause. It
  skips on the direct path, which never reports a cost and is not deployed. It
  needs no database. The first plan put it at the service, with the test
  database, only so that it would send the request production sends; once the
  request became a value, the service level added nothing to the evidence and
  put a retrier and a database between the assertion and the answer. Rejected:
  an end-to-end test through HTTP, the service and the database, which would
  not say where a failure is, and whose one new contribution — the running
  application's wiring — belongs to a smoke test after a deployment (v7).
  Trigger: a multi-step flow whose calls depend on each other's answers, where
  the contract becomes the order of calls the service drives.
- **Live tests are switched on by an option, not selected by a marker.** The
  `live` marker says which tests are live; the `--live` option says whether
  this run may spend money, and without it they are skipped. A default `-m "not
  live"` in `addopts` was rejected because `-m` options do not combine — the
  last one wins — so `pytest -m "not db"` would have run the live test; this
  was checked with the project's pytest. An environment variable was rejected
  because in PowerShell it persists until the terminal closes, so a forgotten
  one would make every later run billed, invisibly. Trigger: none for the
  mechanism; a scheduled CI job passes `--live` explicitly.
- **A run that selects no database test needs no database.** The test-database
  check runs only when a selected test carries the `db` marker, so `pytest -m
  "not db"` and a live-only run work with PostgreSQL stopped; both were run
  that way. The check now trusts the marker, so `db_conn` fails at setup a test
  that uses it without the marker: with the marker removed from one test file,
  its tests errored at setup instead of reaching the database. A test that
  opens its own connection is protected only by its marker; today the one such
  test is in a marked file. Rejected: tying the check to `db_conn` alone, which
  would leave that test unchecked; and deferring, which had rested on the live
  test needing the database. Trigger: database tests that open their own
  connections becoming common — then the check moves to the connection.
- **Warnings stay warnings.** The suite's one warning,
  `StarletteDeprecationWarning`, comes from `fastapi.testclient` importing
  `starlette.testclient`: a dependency announcing its own migration, not this
  code. `filterwarnings = ["error"]` would stop the suite at import today, and
  fixing that means maintaining an exception list or replacing the test-client
  stack. Visible on every run, the warning is its own reminder. Trigger: a CI
  run, where nobody reads the warnings summary (v7), or an upgrade that removes
  Starlette's `httpx` support.

## Documentation and versioning

- **The changelog was split at the version tag.** Until v4.0.0, `CHANGELOG.md`
  did four jobs: `Added`/`Changed`/`Fixed` were a changelog, `Decisions` an
  architecture decision record, `Measurements` the evidence behind it, and
  `Known gaps` an issue list. Measured across versions, the file grew roughly
  fivefold per release — 6, 21, 192, 470 lines — and `Decisions` alone had
  become more than half of the unreleased section. The lifetimes conflict: a
  changelog entry is written once and frozen, while a decision can be
  superseded, and three were during this version; writing a superseded decision
  into a frozen document is what had produced a correction line under an
  earlier changelog entry. The split waited for the version close, which
  rewrote the file anyway. Measurements moved into the decisions that used them
  rather than into a file of their own, which would have left the decisions
  without their evidence. Now the changelog says what changed in each release,
  `docs/decisions/v<N>.md` holds each version's decisions, and
  `docs/known-gaps.md` lists what is open across versions, each entry with its
  trigger. Rejected: keeping one file; and one file per decision — the
  architecture decision record pattern (Michael Nygard, 2011) — which would
  have made this version's decisions dozens of files while nothing refers to a
  decision individually. Trigger: decisions being referred to one by one, from
  code or from pull requests.
- **The version is a property of the code.** The version string was a
  `Settings` field, written in four places — `config.py`, `.env.example`, the
  README's `.env` template and each local `.env` — and a local `.env` overrode
  the code: a line left behind after the release would have made the running
  application report `4.0.0-dev` in its OpenAPI document while the code said
  `4.0.0`. The version does not vary with the environment. It is now
  `app.__version__`, and the application reads it from there; settings ignore
  unknown keys, so a leftover `APP_VERSION` line changes nothing. Rejected:
  updating four places by hand at every release; and deriving the version from
  the git tag, which needs packaging metadata the project does not have.
  Trigger: the application being packaged.
- **Comments state constraints, not step numbers.** Nothing in the repository
  defines the steps the work was planned in, so references to them resolved to
  nothing; the README's roadmap defines versions. A comment either states its
  constraint or points at a version, and the same rule holds for these
  documents.
- **The README keeps what the code cannot say.** The table of contents was
  removed (GitHub generates one), the per-file directory tree was reduced to
  top-level directories, and the feature list was dropped: the tree needed an
  edit for every added migration or test, and the feature list restated the
  changelog. Design rationale that is not derivable from the code — the
  retrieval contract, the testing scope, the evaluation findings — stays.
- **Stale documentation is repaired from a list, not by a sweep.** At the
  version close, documentation was corrected where it was known to be wrong:
  statements this version's own changes had made stale, and a list kept during
  it — a docstring calling the prompt package a leaf although it imports the
  error vocabulary, a comment whose rationale a measurement contradicted, a
  script described as saving what it only prints, counts that change in a
  permanent record, step numbers, and a reference to a test file that does not
  exist. An open-ended review of every comment was rejected: nothing says when
  it is finished or whether it was done right, and it mixes unrelated changes
  into a release. A comment found wrong while working on its file is corrected
  with that work.
